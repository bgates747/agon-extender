# PPA-001 — Identify PPA rendering acceleration opportunities

## Executive summary

Record a deferred assessment of where the current Extender VDP code could use
the ESP32-P4 Pixel-Processing Accelerator (PPA) for clears, rectangular fills,
bitmap/sprite compositing and image transforms. The deliverable is a ranked,
source-linked opportunity report with compatibility constraints and proposed
measurements, not an implementation or a claim of improved performance.

**State: deferred, not started.** On2026-10-05 the Author requests task recording
only and explicitly prohibits beginning the assessment. All subtasks remain
unstarted. No goal, source investigation, benchmark, build, deployment or bench
operation is selected by this record. Begin only on subsequent Author direction.

## Context and dependencies

1. [HDMI-001](HDMI-001.md) owns current fixed720p RGB888 presentation and its
   fidelity, buffering and frame-clock contracts.
2. [BENCH-009](BENCH-009.md) supplies existing deterministic workloads and
   fixed-source conversion evidence. At512×384, RGB888 expansion alone exceeds
   the16.67ms budget for60fps even without scanout. This does not establish
   PPA performance or the drawing performance of a direct RGB888 renderer.
   The longer benchmark campaign remains paused.
3. The Author requires ESP-IDF **5.5.5** documentation for the P4. Its
   [PPA guide](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32p4/api-reference/peripherals/ppa.html)
   documents fill, scale/rotate/mirror and blend operations. It exposes no
   dedicated arbitrary-polygon rasterizer. Rectangular fill is a candidate;
   CPU-generated polygon spans are a separate proposal whose transaction cost
   would need evaluation.
4. Maintained rendering code belongs under `vdp/`, including the project-owned
   vendor tree. Official Agon documentation and reference checkouts remain
   read-only. Pin relevant contracts and exact source identities when the
   assessment begins; do not treat this task record as a completed source audit.

## Scope and boundaries

1. Identify actual current CPU drawing/composition operations that correspond
   to PPA operations. Cover screen clears, solid rectangles, bitmap copies,
   transparent/colour-keyed sprite composition and existing image transforms.
2. Distinguish operations usable with current storage from those requiring
   RGB888/RGB565 assets, a different framebuffer or staging/conversion. Include
   direct RGB888 rendering as a possible prerequisite or alternative, rather
   than assuming the Author has selected that architecture.
3. Preserve VDU behaviour, clipping, logical colours, transparency, drawing
   order, sprite layering, mode-dependent buffering and vblank semantics in
   every proposal. EMOS retains ordinary routing and mode ownership.
4. New indexed/Copper features, browser-output redesign, transport changes,
   arbitrary geometry hardware, implementation and new measurements are
   outside this assessment. Identify existing compatibility dependencies
   without expanding their feature scope.

## Subtasks

### PPA01-01 [ ] Establish the bounded research baseline

Review relevant official Agon contracts first, then implementation details when
material. Pin the current project source and IDF5.5.5 driver/header identities;
check P4 silicon applicability. Prepare a bounded précis with exact source and
documentation links before recommending changes.

### PPA01-02 [ ] Inventory CPU operations and candidate call sites

Trace drawing/composition callers to the actual pixel-writing functions. Record
input/output formats, dimensions, stride, clipping, frequency and buffer owner.
Map each candidate to fill, blend or scale/rotate/mirror; explicitly identify
unsupported operations and CPU fallback responsibilities. Do not infer that
every sprite or copy maps directly to a PPA transaction.

### PPA01-03 [ ] Evaluate integration costs and semantic constraints

Assess asset conversion/staging, cache coherence, alignment, PSRAM traffic,
transaction setup, synchronization, overlap/in-place restrictions and buffer
lifetime. Name the P4 CPU work that PPA would replace and the CPU work remaining.
Evaluate large operations separately from many small operations. Record how P4
VDP would preserve ordering, completion fences and scanout ownership; do not
assume asynchronous submission means drawing has finished.

### PPA01-04 [ ] Rank opportunities and propose bounded comparisons

Produce a table containing operation, source function/link, current CPU path,
proposed PPA path, prerequisites, expected benefit with its evidence/confidence,
memory/semantic risks, implementation effort and a discriminating measurement.
Use existing timings where relevant; mark unmeasured savings as hypotheses.
Keep drawing, conversion, buffer handoff and scanout costs separate. Express
timings in milliseconds and equivalent frames/s, with explicit baselines and
percentage definitions. Propose identical deterministic workloads and software
fallback controls without executing them or resuming BENCH-009.

### PPA01-05 [ ] Present findings for Author selection

Recommend a small first experiment and alternatives, or explain why no candidate
is justified. Record unsupported/rejected opportunities and prerequisites.
Implementation and hardware testing require a separately selected scope; this
assessment's completion does not authorize them.

## Completion gates

1. Every proposed optimization identifies an existing source operation, a
   documented IDF5.5.5 PPA capability and the responsible CPU/hardware actors.
2. The report distinguishes measured evidence, architectural prerequisites and
   performance estimates. It specifies correctness checks and comparable
   timing scopes for any proposed later experiment.
3. Deliver the ranked report for Author discussion. No code changes, firmware
   flashing, production promotion, commit or push belongs to this task's scope.
