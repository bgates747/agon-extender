# TRS-80-003 — Shared P4 services and native-eZ80 / MAME hardware bridge

## Executive summary

The Author assigns Extender ownership of shared P4 integration, the eight-bit
Agon/P4 parallel transport and the eventual EMOS bridge to MAME Model 4 hardware.
First, mame-p4 runs the CPU and devices entirely on P4. Later, Agon's eZ80 should
execute the OS and applications in Z80-compatible mode while P4 MAME supplies
the remaining machine hardware. These are separate execution configurations,
not a proposal to forward ordinary VDU commands to an unmodified MAME driver.

Initial repository review identifies reusable platform services and substantial
native-execution questions: memory-mapped keyboard/video, bank switching, direct
I/O, guest interrupt masking, MAME scheduling and shared UART/parallel pins.
TR03-01 remains the first hybrid feasibility work item: produce a source-backed study and
bounded proof recommendation before implementation. This document establishes
the task and research starting point; it does not declare that study complete.
Subsequent authorized shared-service work extracted the common Ethernet boundary
and reviewed detached runtime ownership; see the completed tranche below. The
peer linked Ethernet/SD/MAME unchanged, but this is not guest/runtime qualification.

## Feasibility issues that must not be hidden by a fast link

1. **Native access interception.** MAME's software CPU calls memory/I/O handlers;
   native eZ80 instructions do not. Identify how every supported guest access
   reaches P4: explicit guest/OS shims, validated patching, a software execution
   layer, or demonstrated hardware interception. Do not assume arbitrary IN/OUT
   traps or memory-write callbacks exist on Agon. Classify unmodified-program
   support separately from adapted LS-DOS applications.
2. **Memory and banks.** Model 4's banked mappings and memory-mapped devices are
   not reproduced by placing a64-KiB image in Agon RAM. Define authoritative RAM,
   video mirrors, keyboard matrix read semantics, bank transitions and coherence.
   Sea Dragon's direct3C00–3FFF writes and3840/3880/3804 matrix reads illustrate
   the gap; its Model III evidence is not Model 4 acceptance.
3. **Interrupts and host survival.** Native evidence includes long DI periods,
   ROM calls, FDC WAIT/DRQ/NMI and direct ports. Define guest versus host interrupt
   state, vector/stack ownership, ADL transitions and recovery. An interrupt-driven
   video copy cannot guarantee progress while native guest code disables it.
4. **MAME time.** Device models depend on scheduler/CPU relationships. Study
   whether to replace/suspend the CPU with a bridge execution device, how time
   advances, how synchronous reads stall eZ80, and when P4 delivers interrupts.
   Simply removing MAME's Z80 device is not an established supported operation.
5. **Transport ownership.** Current eight-bit path uses all eZ80 Port C; UART1
   shares PC0/PC1. Current EMOS rejects parallel entry while UART1 is active.
   Specify quiesce/transfer/drain/restore, keyboard queuing, return data and fault
   recovery. The documented forward pipe is not a proven bidirectional CPU bus.
6. **Latency versus bulk rate.** Historical193–839 KiB/s short bursts are not
   integrated sustained throughput. Benchmark device-read round trips, bounded
   handovers and worst-case interrupt latency as well as bulk video/disk traffic.
   Prefer block/cooperative requests where compatible; per-instruction remote
   transactions may erase native execution's benefit.
7. **Personality and EMOS.** Proposed small versioned service/capability boundary
   must distinguish EDP/VDU from TRS machine operations. EMOS remains transport
   and activation authority; P4 rejects mismatched traffic. Decide whether P4
   uses separate firmware builds or selectable personalities, and whether a
   retained EDP control console is needed. Avoid rewriting ordinary MOS APIs or
   conflating ExCom display routing with entering a different machine.
