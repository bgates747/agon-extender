# MOS-001 — Develop a MOS Modules-aligned cooperative service architecture

## State

- Status: Not started — aspirational; does not gate first-round exclusive modes
- Started: --
- Finished: --

## Namespace

`MOS` identifies work whose primary product is a change to, extension of, or
architecture for the eZ80 Machine Operating System. Scheduling and lifecycle
state are recorded separately and never encoded in the task namespace.

## Prompting discussion

This task was created from
[`REMED-001` Work 2.c, `W2C-Q01`](REMED-001/exclusive-routing-analysis.md#w2c-q01--system-level-routing-family).
That decision accepts a narrow Extender-enabled MOS modification as the
first-round path of least resistance for transparent Exclusive Compatible and
Exclusive Extended routing.

The Author wants a later, more robust system in which independently selected
MOS services can coexist without the onboard VDP and Extender competing for
exclusive hooks, state, response domains, or other MOS/eZ80 resources. A truly
cooperative implementation may supersede Dual mode, become a stronger profile
within Dual mode, or coexist with it as a distinct mode. This task makes no
taxonomy decision in advance.

## Official name and upstream status

The existing official proposal is named **MOS Modules**. Use that name when
referring to the upstream concept; do not coin a competing project name unless
later research establishes that Extender's required system is materially
different.

Current official Agon documentation says MOS 3.0 has no module system but
describes MOS Modules as a likely future facility. The proposal anticipates:

- a permanent Core MOS plus modules loaded from storage at runtime;
- API calls, star commands, C functions, drivers, and unified-I/O providers;
- user-provided modules and registration needed to prevent conflicting API
  implementations;
- the `0x0B0000`–`0x0B7FFF` moslet/module memory area;
- executable declarations for “module safe” and “module compatible” programs;
  and
- possible driver, I/O, non-code, and user-space module forms.

The exact ABI, loader, registry, lifecycle, residency, dependency, and
coexistence rules remain under upstream design. The official starting points
are:

- [MOS Modules documentation](https://agonconsole8.github.io/agon-docs/mos/Modules.html);
- local official source document `agon-docs/docs/mos/Modules.md`;
- local executable-format document `agon-docs/docs/mos/Executables.md`; and
- [upstream agon-mos issue 2](https://github.com/AgonPlatform/agon-mos/issues/2).

Verify current upstream status when this task starts; do not assume the present
proposal, release forecast, issue discussion, or documentation remains current.

## Intent

Research, help mature where practical, and eventually implement a MOS
Modules-aligned service architecture that allows users to compose optional MOS
facilities while preserving explicit ownership and collision freedom. The
prime Extender use case is evolving the first-round EMOS-owned Dual
implementation into a composable cooperative onboard-VDP/EDP architecture
without surrendering either processor's separate state domain.

The result should prefer upstream collaboration and compatibility over a
permanent Extender-only module ABI. A bounded local prototype is permissible
only when its experimental status, compatibility assumptions, and replacement
path are explicit.

## Research work

1. Review the complete current official MOS Modules documentation, executable
   header rules, MOS memory map, APIs, function-discovery machinery, moslet
   behavior, system-variable substrate, and all linked design discussions.
2. Review upstream issue, pull-request, branch, release, nightly, and roadmap
   activity. Record what is implemented, proposed, rejected, superseded,
   controversial, or still undefined; distinguish official decisions from
   individual suggestions.
3. Determine the intended meaning and lifecycle of module registration,
   service/API identifiers, dependencies, nested module calls, loading,
   unloading, replacement, version negotiation, and conflict detection.
4. Determine whether the proposed single moslet/module memory area permits
   multiple services to be simultaneously resident, logically composed through
   swapping, or both. Compare that design with Extender's need for persistent
   transport, interrupts, queues, and asynchronous callbacks.
5. Determine the obligations placed on module-safe, module-compatible, legacy,
   Z80-mode, ADL-mode, moslet, and unheadered programs.
6. Inventory MOS resources that optional services may need to arbitrate:
   interrupt vectors, UARTs, GPIO, timers, VDU routing, response parsers,
   sysvars, completion flags, callbacks, heap/stack, filesystem, command/API
   numbers, and shared memory.
7. Study how a module manager can recover from missing, incompatible, failed,
   unloaded, or upgraded modules without corrupting Core MOS or unrelated
   services.
8. Compare Extender's needs against the upstream proposal. Classify each need
   as directly supported, supportable by an upstream-compatible extension,
   requiring upstream design work, or unsuitable for MOS Modules.
9. Maintain a bounded upstream-change digest so later agents can review small
   semantic changes rather than repeatedly searching the entire discussion and
   codebase.

## Architecture work

1. Define a stable service identity and version-negotiation model aligned with
   upstream registration rather than inventing Extender-only global numbers.
2. Define Core MOS versus module responsibilities and the minimum permanent
   dispatch/registry machinery needed to find optional services safely.
3. Define residency, memory ownership, interrupt ownership, reentrancy,
   concurrency, dependencies, unload safety, failure isolation, and restoration.
4. Define how persistent/asynchronous services coexist with an upstream design
   that may swap code through one 32 KiB module area.
5. Define explicit single-writer and namespace rules for ordinary VDU, EDU,
   VDP packets, EDU results, canonical MOS VDP sysvars, completion flags, input,
   RTC, audio, and mode lifecycle.
6. Define Extender, onboard-VDP, and other optional service registration so a
   user can select useful combinations without silent interception or resource
   collisions.
7. Determine whether cooperative integration:
   - supersedes the first-round EMOS-owned Dual implementation;
   - becomes an optional, stronger Dual profile;
   - becomes a separately named operating mode; or
   - is better described as a service composition independent of mode names.
8. Define discovery, activation, deactivation, dependency resolution, reset,
   recovery, fallback, and capability reporting for every selected composition.
9. Define migration from the first-round exclusive MOS dispatcher without
   breaking its qualified compatibility contract or forcing early users to
   adopt the later module system.
10. Define conformance and qualification matrices covering module combinations,
    resource arbitration, legacy programs, module-safe/compatible programs,
    failure, replacement, and upgrades.

## Upstream and implementation strategy

1. Prefer participation in the existing MOS Modules design and upstreamable,
   hand-reviewable changes over an incompatible permanent fork.
2. Keep research findings, Extender requirements, and any prototypes separated
   so exploratory code cannot be mistaken for an accepted upstream contract.
3. If upstream has implemented MOS Modules by the time this task starts, port
   Extender integration to the tagged upstream facility rather than executing
   this speculative design plan verbatim.
4. If upstream remains incomplete, prepare a precise proposal describing the
   smallest generally useful substrate, not merely a private Extender hook.
5. Split accepted architecture into bounded implementation and qualification
   tasks before changing production MOS or Extender firmware.

## Dependencies and gates

- This task does not gate the first implementation of Exclusive Compatible or
  Exclusive Extended routing selected by REMED-001 Work 2.c.
- REMED-001 and SETUP-005 must first freeze the four-mode architecture and
  initial ownership contracts so this task has a stable predecessor to improve.
- The EDU API and first-round MOS dispatcher provide requirements and migration
  evidence, not a mandatory implementation template for MOS Modules.
- No operating-mode supersession or new mode name is accepted by this task's
  creation. That requires a later reviewed architectural decision.
- No upstream issue comment, proposal, pull request, or code submission is
  authorized merely by this task. Present such external actions for explicit
  approval.
- No production implementation begins until the Author accepts the research
  findings, architecture, upstream strategy, task split, and qualification
  plan.

## Completion criteria

1. Current upstream status and authority are documented with tagged/revisioned
   sources and a maintained change digest.
2. Extender requirements are mapped explicitly to the official MOS Modules
   design, including every gap and proposed generally useful extension.
3. Resource ownership, composition, residency, registration, lifecycle,
   failure, security, compatibility, and migration contracts are accepted.
4. The relationship between the first-round EMOS-owned Dual implementation and
   later cooperative operation is decided and recorded in normative
   architecture.
5. Implementation and qualification are split into approved, sequenced tasks.
6. Any upstream contribution strategy and external actions receive separate
   authorization.
