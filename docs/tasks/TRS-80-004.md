# TRS-80-004 — Shared HTTP/browser-video transport

## Executive summary

Author authorized task definition and implementation on 2026-09-26 after the
TRS-80 VIDEO-01 request. Extract the maintained socket/credit/lease adapter so a
detached consumer injects its frame provider and web assets without importing
VDP/EMOS or starting Ethernet/SD. Preserve console behavior and tested partial-send
handling. Initial consumer needs raw EVF1; console compression remains supported.
No bench switch, firmware promotion or guest integration is part of this tranche.

## Bounded source basis

Existing wired_network_service.cpp owns ESP-IDF socket work, callbacks and F003
short-write workaround; browser_video_service_core owns one-client/credit leases.
OpaqueMessageProvider supplies immutable message views. embedded_assets.hpp is
plain asset metadata; rendering and VDU semantics are outside this extraction.
Current framework is Arduino 3.3.11 / IDF 5.5.5. TRS-80 owns VIDEO-01 pattern,
page and later MAME adapter. No MOS/VDP API, ABI or hardware contract changes.

Keep tracked paths portable; private peer/bench identities belong to mailbox and
machine-local records. This task is a bounded implementation dependency of
TRS-80-003, not completion of its native-eZ80 feasibility or shared-media gates.


## Implementation and validation result

Shared `HttpVideoService` now owns the actual HTTP/WS handlers and queued lease
lifecycle. Console inherits it; provider and static assets are injected. Console
codec selection and routes remain local. Common startup checks asset metadata;
failed route rollback retains the live context if stop fails. Console screen and
display route failure now uses that same containment instead of dropping a handle
without checking stop. HTTP start counters count successful common registration;
a later console-route failure is followed by shutdown rather than undoing history.

| Check | Result | Limit |
|---|---|---|
| Actual adapter with HTTP/socket fakes, ASan/UBSan | Pass | No physical network/task scheduling evidence |
| Asset response/close/error checks | Pass | Fake HTTP boundary |
| P4 console full build/link | Pass; 92.30 seconds; flash 1,566,658 bytes | Unversioned compile only, not deployable qualification |
| Minimal detached consumer using actual P4 compiler/IDF headers | Pass | Translation-unit compile, not peer whole-firmware link |

Lifecycle cases cover no/duplicate credit, raw segmented bytes, short writes,
EINTR, send timeout/failure, queue failure, replacement with pending work, stale
old-client close, queued disconnect/fd reuse, unavailable provider, concurrent
acquisition/replacement, failed start/route registration, failed stop/retry and
restart. Acquired/released counts balance. Older takeover/containment Python
entry points now run this actual-source suite instead of sliced source fakes.

Maintained consumption instructions are in [shared services](../shared-p4-services.md).
The simultaneous default video+SD socket budget is 15 plus other lwIP users;
retained console capacity is 10. Peer must choose explicit limits/configuration
and test simultaneous traffic. No silent console capacity change was made here.

The peer receives the implementation commit as its source pin. Its pattern
firmware link, browser/runtime tests, candidate identity and any bench deployment
remain peer-owned next steps. This extraction changes neither selected production
nor installed firmware and makes no hardware-pass claim.
