# TRS-80-001 — Design TRS-OS integration and reusable network storage for Extender

## State and intent

1. Status: DRAFT design task; initial ecosystem survey completed 2026-09-13.
2. Owner: Agon Extender for product integration and P4 behavior. Component
   ownership follows [OWNERSHIP.md](../../OWNERSHIP.md).
3. Authority: the Author requests a new TRS-80 task to investigate integration
   with the community's TRS-OS work, reusing tools discussed where practical.
4. Deliverable: a source-backed integration proposal, selected first vertical
   slice, explicit component owners, and reproducible qualification plan.
   This record does not claim working TRS-OS support or select a final protocol.
5. Scheduling: survey/design can proceed; reconcile with the active EMOS/EDP
   agent at its stopping point before changing shared interfaces or bench state.
   The existing console/graphics queue and parallel-transport hold remain.

Integrate TRS-OS on Agon with Extender's network and eventual storage/display
services while collaborating with the existing maintainers. Collaborators have
independent repositories and aspirations. The Author's preferred implementation
model is a future owned `TRS-80` project with selected upstream code vendored
under recorded provenance and licenses, rather than forks of every dependency.
Shared protocols and focused reusable patches should permit cooperation without
requiring everyone to adopt one repository.
The first target is TRS-OS on Agon Light 2, not a TRS-80 CPU emulator or a
physical TRS-80 expansion board. Other models belong to later scoped tasks.

## Initial evidence and unresolved boundaries

1. RichL's [trs-os-agon](https://github.com/rlucente-retro/trs-os-agon) provides
   loader source and ez80asm build automation. Its
   [loader](https://github.com/rlucente-retro/trs-os-agon/blob/main/src/boottrs.asm)
   reconfigures memory and interrupts and enters Z80 mode. Its README describes
   a UART0 terminal and UART1 TRS-NET disk service after OS takeover. This is
   not an ordinary MOS application that can keep calling resident EMOS APIs.
2. Shawn Sijnstra's
   [OSboot](https://github.com/sijnstra/agon-projects/tree/main/OSboot) is a
   complementary loader reference. The repository README documents optional
   disk-image/color parameters and says loader source is not yet published.
   At `ed135a709fc398929943658e7dbf1f1a2c28212c`, the OSboot tree contains a
   binary, documentation, font and disk/image assets, but no loader source.
   Preserve its behavior as a comparison baseline; do not assume its source
   is available for adaptation or that a root license settles all asset rights.
3. Daniel Paul Martin's [downloads](https://danielpaulmartin.com/home/my-downloads/)
   are the upstream discovery point for TRS-OS source, system images and
   `TRS-NET.py`. The two archives are now downloaded and CRC-checked on Linux;
   selected server/UART source has now been inspected in
   [the TRS-NET source notes](TRS-80-001/trs-net-source-notes.md). Full build
   reproducibility, guest/server pairing and intended redistribution terms
   still need resolution. Do not equate available source
   with permission to redistribute every bundled OS image or font.
4. The current [ExCom contract](../protocols/excom-console.md) assigns UART1
   at 1,152,000 baud to EMOS and carries display/input traffic. The TRS-OS
   loader's UART0 terminal path and UART1 disk path are a different arrangement.
   TRS-OS cannot simply seize that active UART1 link. Trace the actual UART
   configuration, RTS/CTS, GPIO mux, interrupt and terminal-mode behavior from
   pinned source before selecting wiring or a mode transition.
5. The bleeding-edge [mainboard SD service](../mainboard-sd.md) runs through
   foreground EMOS `sdserve.bin`. It cannot be assumed to remain alive after
   TRS-OS takeover. Its HTTP file API is not a TRS-NET disk protocol. Reuse
   tested transport/lifecycle ideas where appropriate, not an unsupported
   promise that the existing service works under another OS.
6. The Author reports that another agent can now type at the Agon CLI. Treat
   that as a changing bench capability until its owner supplies the current
   committed contract and evidence. CLI automation is separate from the SD
   API and does not prove keyboard delivery after TRS-OS replaces EMOS.

The [community discussion](https://discord.com/channels/1158535358624039014/1548415432648827021)
motivates this task. Maintainer reports about ongoing SD support, wireless
experiments and prospective bridges are leads to reconcile with source, not
Extender acceptance evidence. Keep private conversation exports and machine
access details out of tracked task material.

## Reuse comparison to perform

| Candidate | Proposed role | Evidence and question to settle |
| --- | --- | --- |
| TRS-NET / `TRS-NET.py` | First compatibility baseline for the existing TRS-OS disk driver | Recover exact framing, disk geometry, baud/flow control, errors and write semantics; test a P4 relay to the existing host server before replacing either endpoint |
| [NHACP](https://github.com/NHACP-IF/NHACP-specification) + [nabud](https://github.com/thorpej/nabud) | Alternative existing remote storage protocol/server | NHACP covers block and file operations; determine TRS-OS driver cost, selected version, transport framing and actual nabud interoperability |
| [DriveWire](https://github.com/DrPitre/DriveWire) + FujiNet | Alternative disk interface with community tooling | Verify the precise software bridge RichL used, supported operations and TRS-OS driver work; do not infer that a CoCo driver runs unchanged on eZ80 |
| FujiNet / TNFS | Possible network backing-store layer | Separate remote file access from guest disk semantics and the eZ80 wire protocol; identify supported image formats, writes, flushes, retries and server behavior |
| MOD-WIFI-ESP8266 | Optional transport experiment | Compare eZ80-controlled module costs with P4 network offload; establish UART/pin ownership and firmware mode first |
| Fab + ez80asm | Loader/guest regression harness and assembler | Reuse canonical tools; verify memory remapping and UART1/server test support rather than assuming ordinary MOS filesystem interception covers TRS-OS |

identifies protocol 0.1. nabud documents serial and TCP-connected clients.
These are survey facts, not a selected implementation baseline.

is an Atari SIO/NetSIO bridge; it does not establish the identity of the
DriveWire-to-FujiNet software bridge mentioned in the discussion. Resolving
that exact tool is part of work package 1. Other fetched branch-head documents
are discovery references; pin their revisions before copying/building them.

## Work packages

1. **Freeze the survey inputs.** The integration maintainer inventories both
   loaders, Daniel's OS and TRS-NET archives, NHACP/nabud, DriveWire, FujiNet
   and TNFS. Record exact URLs, versions/commits, archive and binary hashes,
   source/build availability, license notices and known maintainer work.
   Compare loader behavior and identify reusable upstream changes versus
   Extender-only adaptations. Prepare concrete questions for collaborators;
   sending messages or opening upstream issues is separate authorized work.
2. **Resolve takeover and console ownership.** EMOS and Extender owners trace
   memory banking, ADL/MADL/MBASE, vectors, timers, UART0/1, flow control,
   GPIO and display/input across prepare, handover, guest run, failure and
   recovery. Compare two designs: a negotiated standalone guest handover,
   or a deliberately preserved EMOS service environment. The latter requires
   evidence that it can coexist with TRS-OS's memory/interrupt model. Neither
   is an implicit exception to the current EMOS ownership contract. Start by
   considering the stock VDP terminal as a baseline; P4 terminal/input support
   is a separate requirement, not implied by stock VDU rendering.
3. **Choose the smallest storage slice.** Compare a bounded P4 UART-to-host
   TRS-NET relay, a P4 TRS-NET-compatible server, and a new guest driver for
   NHACP or DriveWire. Prefer the option with demonstrated reuse and the
   smallest necessary changes, measuring correctness and recovery before
   throughput. Specify which actor parses each protocol and which actor owns
   persistent media. Keep backend selection independent of terminal selection.
4. **Define persistent-media semantics.** Name the Agon mainboard SD card,
   P4 DevKit microSD card, guest RAM disk, emulator image and host backing
   file separately. Never use “the SD card” without its owner. PORT-007 owns
   the planned P4 microSD service; it is not implemented by this task's survey.
   Determine sector sizes, image geometry, bounds, read-only mode, writer
   exclusion, cache/flush guarantees, disconnect/retry behavior and recovery.
   Prevent concurrent host and guest modification of a mounted disk image.
   Start qualification with disposable copies and a read-only mount.
5. **Prepare an isolated proof plan.** First reproduce a known loader/OS/stock
   terminal baseline, then one guest disk read through the selected P4/host
   route, then controlled write/restart/readback. Use canonical Fab profiles
   under project-local ignored `.emulator/`; generated wrapper, pinned firmware
   and explicit SD mapping are required. Directory-backed MOS FatFS shortcuts
   do not prove guest bare-metal SD support. Use raw media or an actual serial
   peer where required. Native VDP modules and P4 firmware are different build
   products. Keep host-only tests distinct from physical UART/board evidence.
6. **Record the implementation decision.** Publish an actor-explicit ADR and
   component contract identifying the selected baseline, rejected alternatives,
   compatibility promises, error paths and next implementation-sized tasks.
   Promote shared decisions through `agon-dev-env`'s cross-agent contract
   convention before changing independently owned interfaces. Each owner
   indexes its implementation in its own authoritative TODO; this task retains
   only the product integration requirements and links.

## Acceptance criteria for this design task

1. A pinned source/provenance inventory distinguishes inspected source,
   binary-only references, maintainer reports and remaining unknowns.
2. The proposal assigns every transport, interrupt, memory region, media
   backend, console path and recovery action to an actor in every run state.
   The EMOS takeover conflict has a concrete supported disposition.
3. A protocol comparison covers reuse, driver and adapter cost, licensing,
   buffering, flow control, retry/duplicate handling, durability and host/P4
   resource cost. No unsupported performance figures become acceptance goals.
4. The first slice has exact expected observations: identified guest boot,
   terminal input/output, disk read; subsequent writes survive a controlled
   guest/server restart and match independent backing-file readback. Include
   malformed requests, absent/full media, link loss and interrupted writes.
5. The plan preserves existing Legacy/ExCom operation and the active bench
   candidate. It defines recovery without assuming a safe automatic Agon reset
   or that MOS return is possible after takeover.
6. The Author has a reviewable architecture, identified implementation owners
   and qualification sequence. This task can close on an accepted design;
   working firmware requires separately recorded implementation evidence.
