# NET-004 — Parallel carrier for application network messages

Carry application network messages between eZ80 and P4 over the existing
bidirectional parallel wiring, preserving mainboard Legacy graphics and the
bounded TCP/message framework. The previously exercised NET-003 carrier uses
UART1; it does not meet this requirement. This task changes the carrier rather
than the game protocol and keeps scarce EMOS flash and CPU costs explicit.

## Authority and state

Smith requires parallel network payload in both directions for MechAgon and
delegates ABI agreement to Extender and MechAgon on2026-11-05. Publish this plan
before implementation. Extender owns P4/service transport and maintained EMOS
changes; MechAgon owns its consumer/bridge/module. Coordinate mainboard UART0
RFC25 with the UART owner. No bench preemption, firmware installation, production
promotion or emulator change follows from source implementation authority.

## Invariants

1. EMOS owns shared Port C, UART1 parking/return and transfer admission. The
   application uses an owner API, never raw GPIO/UART or a display-route bypass.
2. All network application records/results cross the parallel pipe. UART1 may
   retain keyboard and small carrier-control traffic; no payload fallback.
3. Keep Legacy UART0 mainboard graphics independent. Parallel service access
   must not require committing an ExExt display route.
4. Reuse the NM envelope,128-byte application payload,32-bit session/query,
   two-slot bounded network queues and outbound length-framed TCP. P4 owns
   sockets; application/bridge own game turns, deadlines and interpretation.
5. One admission per bounded transfer; no per-byte acknowledgement, checksum,
   automatic reconnect or uncertain replay. BUSY admits no caller data.
6. Prefer application buffers and foreground service over resident queues,
   diagnostics and arbitrary callbacks. Separate source release, pipe drain,
   P4 admission and remote application consumption.
7. Preserve UART0 TX/RX and callback state, ordinary UART1 input and startup.
   The first consumer may serialize pipe epochs against outstanding UART0 TX
   and required receiver replies. Measure IRQ/service gaps before overlap claims.
