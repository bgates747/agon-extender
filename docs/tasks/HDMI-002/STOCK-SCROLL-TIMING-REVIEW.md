# Nurples mode 20 — mainboard VGA and Extender P4 scroll timing

**November 21, 2026 · Offline review for Smith.** Smith reports smooth scrolling on the mainboard VDP and uneven movement at different heights of the playfield on the Olimex P4 candidate. The closest code-level match to that difference is the P4's presentation of single-buffered games. Stock prepares two logical rows at a time in step with physical VGA scanout. The P4 port preserves the scroll primitive and a hardware-paced drawing opportunity, then independently converts a whole image from live rows into the HDMI buffer being scanned. This creates two distinct opportunities to put old and new terrain into one displayed image. The gameplay interval has no frame capture or trace to identify which occurred. The brief blackout is deferred.

## What both renderers do with a scroll

Nurples selects single-buffered 512×384, 64-colour mode 20. During normal terrain travel the eZ80 asks EMOS to send `VDU 23,7,2,2,1` for a one-pixel downward scroll of the 256×336 graphics viewport at (128,48). It then restricts the viewport to the newly exposed top line and sends separate bitmap plots. EMOS routes ordinary VDU over the mainboard UART in Legacy or the Extender display UART to the P4 in ExCom. Both parsers set the scroll region and call `Canvas::scroll`, which queues a vertical-scroll primitive in this mode. The VGA64 routine walks the affected rows bottom-up, preserves the side strips outside the viewport, swaps row pointers and fills the exposed pixels. Compared as source text, the bodies of `Canvas::scroll`, `VGA64Controller::VScroll` and its pointer-swapping `genericVScroll` overload are identical in stock and the tested P4 tree. The scroll and the game's subsequent redraws are separate operations. [VDU contract](https://github.com/AgonPlatform/agon-docs/blob/f9806bd3cbff6ed5d1c08bef1d51fed11764b86b/docs/vdp/VDU-Commands.md#L275) · [Game command sequence](https://github.com/bgates747/nurples/blob/7acfbfa3f27c0100afbedc9d40d75a98a4d1e846/src/asm/tiles.inc#L117) · [Stock parser](https://github.com/AgonPlatform/agon-vdp/blob/c7ac293d2aa81ddfa693390549bcd909069c8fc3/video/vdu_sys.h#L774) · [VGA64 vertical scroll](https://github.com/AgonPlatform/vdp-gl/blob/ac2dd5986daf496c43ae8e7fe41836274aec54a0/src/dispdrivers/vga64controller.cpp#L352) · [Viewport row algorithm](https://github.com/AgonPlatform/vdp-gl/blob/ac2dd5986daf496c43ae8e7fe41836274aec54a0/src/displaycontroller.h#L2941)

| What releases queued drawing? | An I²S DMA descriptor interrupt stages the last pair of visible logical rows, advances the VDP frame counter and wakes the primitive worker when eligible. This gives drawing a repeatable start relative to the VGA raster. | The DSI driver's whole-frame DMA completion callback advances the VDP frame counter and wakes the drawing worker. | Must drawing finish in vertical blank? | Mode setup enables background execution and explicitly disables the optional primitive timeout. The worker drains until empty or suspended, then performs the final software-sprite update. Some other API calls can explicitly drain the queue immediately. Stock allows work to extend into active scan. | Mode setup makes the same settings. The port's drawing worker drains in order and updates sprites, with native exclusion around each operation. The physical I²S setup and optional CPU-cycle budget calculation are omitted in this runtime. The disabled stock timeout supplies no missing deadline to reinstate. |
| When does an output row acquire its pixels? | The VGA64 driver uses four short signal buffers. At an interrupt every two logical rows it copies and decorates the next pair from the visible viewport for the ring. Mode 20 uses physical double scanning. The raster determines the lookahead. | After draining, the drawing worker wakes a separate output worker. It samples and decorates logical rows from top to bottom, takes and releases the native mutex for each row, and expands each to RGB888 outside that lock. A later drawing batch may execute between two row reads. The worker coalesces pending frame notifications and blocks for one scheduler tick after a pass to give other tasks execution time. |
| Where can DMA see a new image? | The VGA signal ring already holds the prepared pair when the peripheral reaches it. Stock has no separate whole-frame RGB888 conversion streaming changes into the active scan buffer. | Although two 684×384 panel buffers were allocated, `(scaled || display.isDoubleBuffered())` is false in mode 20. The P4 selects the current HDMI front for writes. The driver writes cache rows back and selects that buffer for scanout. The logical-swap generation check is gated on double-buffered output and would only detect a logical swap. Ordinary mode-20 scrolling changes pixels without one. |

## Ranked findings for the reported motion

The order reflects which mechanism can directly explain row-dependent motion and which can be isolated with the smallest change. An earlier, different hardware-sprite Nurples trial also recorded a thin P4 tear that disappeared on pause and smooth mainboard output. It supports using pause as a control. Its build, game configuration and symptom differ from this playthrough. [Earlier observation](MEMORY-RESULTS.md#author-play-review-and-pause-follow-up)

1. **The destination can change during physical scanout.** The P4 compositor and DMA can use the same RGB frame buffer at the same time. The monitor can therefore receive an earlier terrain position in one group of rows and a later position in another, even from an internally consistent source pass. Which rows DMA saw depends on the actual writeback and fetch times. This is the smallest independently testable difference because the candidate already allocated a second physical buffer. The P4 HDMI port introduced this policy in `e88fe022`. The decision explicitly acknowledged that single-buffered output may tear. [Original HDMI port](https://github.com/bgates747/agon-extender/commit/e88fe02240ff49a591e18b20ccab2800cbaf97a2) · [Buffering and clock decisions](../HDMI-001.md#decision-register)
2. **A completed P4 conversion can itself contain two scroll positions.** A one-pixel scroll may finish after the compositor reads upper terrain and before it reads lower terrain. Each row and each primitive can respect its lock. The mixed result survives even if the finished conversion is displayed from a perfectly isolated buffer. A steady DMA frame count and zero logical swap drops are compatible with this outcome. The original P4 renderer deliberately separated drawing, frame progress and browser output. The HDMI port reused the row reader. Earlier work verified quiescent row content and recorded both mixing mechanisms as open under load. [Original P4 frame service](https://github.com/bgates747/agon-extender/commit/57a0d86125ef5974c03db31d895de9aa0bba1e35) · [Row-exclusion decision](../PORT-003/stock-backend-restoration.md) · [Row tests](../PORT-003/stock-backend-r2/README.md) · [Earlier HDMI finding](../HDMI-001.md#h001-f01--excess-sprite-flicker-remains-open)
3. **Nurples paces itself from a different display clock in ExCom.** After its update the game waits for a change in the low byte of MOS `sysvar_time`, with a 65,536-poll fail-open bound. Mainboard ESP32 GPIO15 supplies VGA VSYNC to eZ80 PB1. The EMOS interrupt advances the clock by two per edge. In Legacy the game and the visible display share that VGA generator, albeit at different phases. In ExCom the mainboard continues scanning its status display and clocking PB1, while the P4 presents on its own HDMI DMA clock. ExCom entry does not set the mainboard mode. Its retained refresh rate and its phase relative to HDMI are unknown for the playthrough. This can change which draw batch takes a scroll or cause an entire update to repeat or skip. Different movement at different heights points first to findings 1 and 2. [Game wait](https://github.com/bgates747/nurples/blob/7acfbfa3f27c0100afbedc9d40d75a98a4d1e846/src/asm/vdu.inc#L213) · [EMOS interrupt](https://github.com/bgates747/agon-emos/blob/abefa2f943eb3089c08d85bf39e48ebb4938f4bd/src/interrupts.asm#L42) · [ExCom entry](https://github.com/bgates747/agon-emos/blob/abefa2f943eb3089c08d85bf39e48ebb4938f4bd/src/emos_console.c#L197) · [Physical wiring](../AUDIT-004/trace-hardware-and-dependencies.md) · [Display routing](../../architecture.md)

The static mode-20 preview quantifies the scheduling limit. In a 10.008 s window, the P4 reported **29.445 ms mean / 32.287 ms maximum conversion**, **32.174 submissions/s** and **60.051 DMA frames/s**. One mean pass occupied about **1.77 refresh periods**. The candidate timing gives a nominal 16.65 ms period and 4.28 ms of vertical blank (133 blank lines × 1,104 pixel clocks ÷ 34.286 MHz). Moving the worker wake to VSYNC alone cannot fit a pass of that duration into blanking. These are wall times for a static picture. The game has no measured conversion time, publication rate, or timing of a tear. ## Proposed discrimination, pending Smith's review

1. Use the same staged Nurples executable and assets, opening level, input sequence and pause interval in mainboard Legacy and candidate ExCom. Record the mainboard mode/rate entering ExCom. Score complete frames at the same terrain landmark at the top, middle and bottom, with the HUD as a fixed reference. Keep the monitor, processing settings and capture cadence comparable, and record the distinct VGA/HDMI signal paths. Whole-frame repetitions and displacement that differs by height need separate counts. The two P4 carriers alone share both suspect mechanisms.
2. For the first P4-only comparison, keep the candidate carrier, renderer, game, source-row reader and **logical single-buffered mode 20**. Have the P4 write only the available spare HDMI buffer, then select it when complete. Confirm the driver has armed that buffer before releasing the old front for reuse. Record actual buffer indices, conversion/submission times and displayed terrain motion at comparable cadence. Disappearance of the bands implicates active-front writes. A slower handoff can mask the symptom, so record that difference. Qualifying a repair would require reproducing and resolving the effect under comparable gameplay load.
3. If bands persist with exclusive destination ownership, instrument scroll execution against top/middle/bottom source-row reads and DMA frame numbers. Tag samples with the completed scroll count in the same native exclusion as the row read. A count transition within one converted image directly demonstrates mixed source terrain. Compare with a coherent native image captured at a controlled drawing boundary, releasing native state before RGB expansion. Measure capture cost and delivered cadence. If captured frames move as a unit but at irregular intervals, correlate the mainboard game tick, P4 draw wake and DMA cadence on a common clock.
