# Native-row P4 HDMI candidate and offline verification

**November 21, 2026.** Smith approved a P4-only implementation for all stock applications. The P4 now samples stock display rows at DMA-paced intervals, converts each composed pixel once, and fills three internal RGB888 slots. The eZ80, EMOS, installed mainboard VDP and games keep their existing contracts. The [load-test packet](NATIVE-ROW-LOAD-PACKET.md) awaits review before an Olimex reservation. Physical scrolling behavior, monitor lock, allocation success on the installed P4, and loaded refill headroom are open.

## What changed during a frame

1. The P4 DW-GDMA interrupt retires one 32-physical-row block. One core-1 worker owns the freed slot, reads the next native rows under the stock guard and handles palette, Copper and overlays in their existing order. It releases the native guard before converting to the panel's BGR byte order. A fresh clean slot inherits its DMA-visible black borders. A reused dirty slot clears exposed pixels on a geometry change.
2. In 320×240 modes the worker writes each completed colour directly to four final positions in 848×480, starting at (104,0). For 640×240, it repeats only the row. Mode 20 remains logically single-buffered, at 512×384 centered in 684×384 with 86 black columns on each side. Each stock double-buffered mode retains its queued logical swap.
3. The worker releases core-0 drawing after the last source rows of a frame have been staged. It gates the top of the next frame until DMA enters the final block. A pending double-buffered draw batch completes before the next top row is read. Single-buffered drawing and row production can overlap. Only the hardware full-frame callback advances the public frame count. P4 scheduling granularity is 32 physical rows. Stock VGA64 schedules native rows in pairs.
4. The descriptor for a future frame/block stays invalid until its exact slot is ready. The producer completes stores, synchronizes a changed slot, validates its tag and elapsed time, fences, and arms the descriptor. The worker checks the time again following the marker write. It charges queueing, phase wait, rendering and visibility to the same 1,600 µs budget. A 16 µs pre-arm reserve is an implementation allowance. It still needs measurement. An invalid descriptor, underrun or late refill stops DMA and latches the first fault for retrieval outside the drawing path.

## Copies, allocations and remaining work

These are selected-path payload sizes in bytes. They exclude allocator overhead. For the panel allocation, the control requested a pair, with a possible single-frame fallback at 684. The previous mode-8 scaler requires the pair at 848.

|---|---:|---:|

| HDMI-only browser snapshot pixels in PSRAM, three 1024×768 slots | 2,359,296 B | 0 B |
| Two 684×384 RGB888 panel frames in PSRAM | 1,575,936 B | 0 B |
| Private 320×240 RGB888 scaler source in PSRAM | 230,400 B | 0 B |
| CPU intermediate write + PPA source read per completed mode-8 scale | 230,400 B + 230,400 B | 0 B + 0 B |
| Whole-848-carrier wrapper cache requests per completed mode-8 scale | 1,221,120 B clean + 1,221,120 B invalidate, plus SDK and submit operations | 0 whole-frame requests |
| Three 32-row DMA pixel slots in internal SRAM, 848 / 684 | 0 B | 244,224 B / 196,992 B |

1. With the panel pair, these removals total **5,031,936 B at 848** or **4,165,632 B at 684** of previous PSRAM pixel backing. At 684 with the control's one-frame fallback, the corresponding figure is 3,377,664 B. The bench packet records free heap and fragmentation separately. Each native slot requires a contiguous aligned internal allocation of 81,408 B or 65,664 B. The dedicated 8,192-byte whole-frame publisher stack and periodic publisher work disappear. The new refill task has a 6,144-byte stack plus task/queue/descriptor control storage. The automatic carrier reconfiguration worker is still required.
2. Mode 8 samples 240 decorated rows and 76,800 logical colours. It writes 921,600 final RGB image bytes. Display DMA still reads 1,221,120 carrier bytes including borders. Mode 20 still writes 589,824 visible RGB bytes. The old full-frame publisher already wrote those values directly into panel storage. Removing it eliminates independent whole-frame publication and active-front writes. It does not eliminate the final pixel writes. The old full-frame path never paid the historical rolling backend's DMA2D background-strip copy.
3. The worker retains a 1,024-byte aligned row scratch for per-depth expansion, decoration and safe ownership after dropping the native guard. The refill path requests one C2M synchronization per changed slot, covering 81,408 B or 65,664 B. The driver elides the request for already DMA-visible black slots that stay black. Cache request lengths are different from measured external bus traffic. Physical throughput, CPU cost at an idle prompt and cache/bus utilization need matched measurements.
4. Both rendered output rows are in the same slot. A completed group of RGB values can be used for both rows without reading a completed RGB row back. The native path uses one descriptor per 32 rows. The P4 bridge has a four-bit block-count field and the 480-row carrier already uses all 15 blocks. Per-row descriptor repetition requires a different hardware scheduling design and proof. The direct two-row implementation keeps the reviewed descriptor ownership and exact output. Inspection of the first target build showed GCC splitting the second row into twelve byte stores per four output pixels. The final producer supplies the verified row alignment. For one pair of four-pixel spans GCC emits three word stores per row and reuses the same three registers. Mode 8 therefore eliminates 345,600 output-store instructions per frame relative to that intermediate build. The two implementations write the same number of final bytes. Throughput and bus traffic need a target measurement.

## Physical verdict to collect

Both carriers consume 32 active rows in a nominal 1,030.4 µs. Slot reuse after two such intervals gives approximately 2,060.8 µs before hardware prefetch and observation uncertainty. The next-frame block-0 request normally spends one interval waiting for the drawing opportunity. That leaves about **570 µs** of the software guard for the rest of that job, including final publication. A clear, scroll or delayed swap can consume it. A stopped parser waiting on a swap may need the independent HTTP/serial fault capture and the commissioned recovery procedure.

The [packet](NATIVE-ROW-LOAD-PACKET.md) compares mainboard VGA, the prior P4 at matched carrier timings and this P4 using the same programs and assets. It records static, scrolling/paused, swap, clear, transition, transport and soak windows. The software guard uses ISR delivery time. Software ready-to-next-callback lead includes the frame seam. To qualify the physical deadline the operator also needs an independent retirement and earliest-fetch witness or a validated conservative bound. The software histogram and a stable monitor cannot supply it. The separate transient-blackout investigation remains deferred.
