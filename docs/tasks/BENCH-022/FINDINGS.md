# Where the Olimex bench runs failed

**Standardization caused some of the stops. The strongest recurring problem is that an operator can restore a changed board after a successful test with a shared command, but often needs a new program to do exactly that after a failed test.** Human-run jobs have a similar gap between staging and handback. The shared app0 programmer now has a good record on matched writes. Three later USB connection failures deserve investigation on their own. The available controls do not establish progressive hardware degradation.

## How the review was done

The window is November 12 through November 19, 2026 at 14:27 Eastern. Extender reconciled the old registry events, new FIFO chat-delivery records, operator check-in records, local job packets and original parent receipts. There were no legacy registry events on November 12–15 between releases 181 and 182. The [local custody index](../../../agents/bench022/custody-index.json) identifies 19 historical registry events and 147 Pi scheduler message receipts in the window. These are transactions, so several can belong to one reservation. The new FIFO is a current-state document. Direct desktop messages need not have a Pi sender receipt. The worked-example, fputs and original rehearsal logs supplement the delivery inventory. This is a reconstruction of recorded bench activity, with no estimate for unrecorded manual use.

The [phase ledger](PHASES.md) gives each indexed invocation, timestamp, duration, exit status, join and evidence directory. The linked local JSON adds the actual argv and manifest pins where recorded. Production moved during the window. The owner baseline before parallel promotion included P4 `d9bcb1a2`, EMOS `a25f1612` and later mainboard `dc43ecb8`. The promoted P4 and EMOS were `539dc717` and `9b90b5d9`, with listener `98492acc`. The mainboard subsequently moved to `90edc4c5`. Every comparison below uses the specific job's component selection. Raw argv, private host configurations and captures remain at their evidence locations.

Operators were asked once each about gaps. Extender inspected its own original evidence and retained cold-operator journals. The replies are indexed below. A status of “passed after recovery” retains both the original fault and the successful return. An accepted reservation, a good programmer checksum, a working CLI and a guest pass each answer a different question.

**Proposed approval wording.** The operator uses the commissioned phase commands and job manifest. Before writing or changing executable code that accesses the bench, sequences target actions, changes their prerequisites, or performs recovery outside those commands, the operator must obtain Smith’s explicit approval. State the unsupported action, the shared command checked and the proposed scope. This includes job-local wrappers and inline commands that implement new target behavior. An ordinary fixture, offline analyzer, or documented invocation of an existing phase remains routine. Extender owns recurring runner features. A failed test follows the existing custody and notification procedure.

The most useful test of a new runner feature is a saved failure **and** a corresponding success through the operator’s actual entry point. Filename/manifest preflight alone missed both VDPlet errors. Existing shared facilities already handle ordinary app0 writes, paired multi-file staging, result collection and native UART plus an independent completion witness. Those operations need no replacement based on these records.

## Why these gaps survived commissioning

The [current guide](../../operations/olimex-bench/README.md) explicitly describes stopping before RUN for a human-start job. The [runner](../../../scripts/olimex_bench.py) constructs a different executable sequence. Its phase list includes fixture runs, its `invoke` method advances directly from LOAD to RUN, and its worker verifies every earlier phase as successful before it calls restore or handback. The narrower install retry is a special case. Thus a commissioned packet can obey the written invocation boundary yet still need a custom handback. This is a defect in the fit between the guide and the executable procedure. Printing a clearer command in the guide alone cannot fix it.

The original cold acceptance exercised a complete, successful automatic sequence. It did not qualify continuation from a failed arm or manual return. The later VDPlet host check tested preload and pinned the inputs. It did not feed the installer output into the actual parser, or call both CLI checks in one phase directory. Those are testable on the host before any device access. The shared implementation itself calls the observer with encoded markers, and the receipt writer deliberately rejects overwrites. The proposed change keeps that protection. [CLI observer](../../../scripts/olimex_cli.py) · [Process and evidence handling](../../../scripts/bench_process.py)

There was also a real mismatch between the earlier curated staging instructions and Smith’s transfer policy. They commissioned UART and payload readbacks. The production two-way PARLIO promotion superseded them. The subsequent P4 error on a particular MP008 transfer was explicitly reported by the transport; nothing in its record demonstrates silent corruption after reported success. Returning to routine fixture checksums or rereads would not address the recorded failures. [Transfer audit](../BENCH-021/RESULTS.md) · [Matched qualification](../PORT-008/PRODUCTION-SD-PARALLEL-R03-RESULT.md)

## Audit checks and limits

- Extender compared the complete saved programmer readback against the saved write image for all twelve matched operations. Each also matched its independent verification digest and recorded boot/CLI readiness. The comparison used existing Pi files.
- Extender checked the first-session programmer logs and terminal records for all eight named FSIM phases, both retry records, and the separate Nurples inherited-restore failure. The three failing logs report download-mode detection without a sync reply. None records a flash erase or write in progress. No trace establishes an electrical cause.
- The 232 indexed supervision records include 200 recorded zero exits, 31 nonzero exits and one missing parent wait result. These counts mix primary, admission, diagnostic, and recovery phases. Some earlier operators used different journal formats. Individual programmer commands and human actions are not additional phase rows. One human-held wait test still had production restoration pending at cutoff.
- The most informative physical control, if later selected, is to repeat the same USB entry from a documented start state and compare with the same entry after the paired reset. Keep the extra wiring fixed for the first comparison. Record failure before sync, after sync, during flash access and after restart separately. Unplugging wiring at the same time as changing reset behavior would lose the comparison.
