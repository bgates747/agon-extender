# Controller timing results — 2026-10-26

The deterministic source reproduces substantial delay and loss before EMOS or
the Agon viewer is involved. Oryx sends on schedule, but the P4 acknowledges
only about19% of120Hz traffic, with261ms median round trip. The Pi reproduces

blocking point has not yet been measured.

## Independent observations

1. Oryx sent30 ICMP echo requests during the lower-rate investigation; all30
   returned. Kernel ping min/average/max was0.319/0.558/0.822ms. This uses a
   different responder path from the controller socket, so it is a network
   control, not an equivalent latency benchmark.
2. A bounded Oryx Ethernet capture retained313 matching STATE/ACK pairs during
   low-rate cases. Capture-timestamp round trip median28.713ms, p9588.011ms,
   worst182.312ms confirms delay before Python receives ACKs. The partial
   capture window and kernel realtime timestamps are separate from monotonic
   application logs; no full-run packet-loss rate or clock sync is inferred.
   Tcpdump reported zero kernel drops.
3. In the Oryx120Hz baseline,456 ACK gaps exceeded10ms. Of those,454 (99.56%)
   lay within2ms of a multiple of53.333ms. Overall gap median was53.147ms;
   some ACKs arrive in short clusters. This is an observed service pattern,
   not proof of a53ms RTOS tick or a particular blocking call.

## Source attribution and prepared scheduling control

1. `vdp/video/extender/input/controller/runtime.hpp` in installed source runs
   `controller-udp` at priority2, processes at most8 datagrams per iteration,
   and requests a2ms/two-tick block. The installed SDK configuration records
   FreeRTOS1000Hz. Installed ELF disassembly independently confirms
   `vTaskDelay(2)`; we have not measured actual sleep duration.
2. `vdp/video/video.ino` pins the parser at priority3/core0.
   `vdp/video/extender/display/stock_p4_service.cpp` creates drawing at
   priority5/core0 and ordinary output at priority6/core1. Its output loop
   explicitly documents long (~50ms historical) conversion passes starving
   lower-priority work and blocks one tick to give such work a chance.
   That historical comment is supporting source context, not a new measurement
   of the currently active conversion duration.
3. Together these observations make low-priority worker starvation a strong
   hypothesis. The smallest prepared control raises only the controller worker
   to priority4. It can preempt the priority3 parser while remaining below
   drawing/output; it retains the packet budget,2ms block, existing wire
   formats and all EMOS/mainboard firmware. It does not busy-spin or change
   processor-link integrity handling.
4. The exact installed-source control is committed as `0c007438`, parent
   `27d93dcc`, branch `codex/input002-priority-control`; maintained controller
   source carries the same patch. Only the worker priority/comment differ.
   The canonical indexed-PPA builder refuses an unversioned sentinel and
   requires an Author-approved `indexed-hdmi` revision. **No control binary
   has been built or flashed.** Propose the unused next revision r14 for this
   comparison; agreement and identified build/verification precede deployment.
5. If the control remains slow, instrument P4 loop entry, actual delay return,
   RTOS tick delta versus `esp_timer`, mutex acquisition, `recvfrom` and
   `sendto` duration. Retain one build at a time and compare the same offered
   workload. Do not assume that raising priority alone proves the cause.

The viewer has separate downstream limits: it requests through EMOS at most
every2 raw MOS units and paints every6, nominally60/20Hz. Drawing and gateway
polling share its thread. Raw MOS time advances two units per physical VBlank,
so these are not an independent120Hz timer. None of the physical UDP cases
measured the additional gateway/render/presentation delay.
