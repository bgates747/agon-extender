# EXT-004 — Bitmap, matrix, and sprite demonstrations

**Status: Completed and visually accepted by the Author on 2026-09-08.
All 32 pages are deployed as 123 keypress stages.
Full-tour and isolated runs pass 95/95 pixel checks;
41/41 independent presentation comparisons pass. See
`../bitmap-reference-observations.md` for renderer interactions and contracts.**

## Objective and presentation

Build `bitmaps.bin`, a companion to Shapes, using the Blender axes artwork to
exercise bitmap loading and plotting, 2D matrix transforms, and the VDP's
software and hardware sprite APIs. Exercise the imported library entry points
as well as commands missing from that snapshot. Retain documented commands
even when Extender does not yet implement them; Extender's agent owns readiness
review and any explicit local skips, as the Author already directed.

Use the established **mode 20: 512 × 384 pixels, 64 colours, 60 Hz**,
selected before launching the application. Keep the top 48 pixels for the
page number, command family, and expected result, with labelled comparison
panels below and key instructions in the footer. Most tests use pixel
coordinates; mark the origin and coordinate convention on exceptions.

Use the accepted `waitKeypress` controls. Any non-Escape key advances one
labelled stage, or the next page when the current page is complete. Movement
and animation are stepped by keypress so each result can be inspected.
Escape works at every stage: hide/deactivate sprites, release owned resources,
restore normal text state, clear the screen, and return to MOS. Normal completion
also removes live sprites and restores MOS state; preserve the final static
summary. Support isolated page selection, numbered 1–32, as well as the tour.

## Source asset and reproducible derivatives

The matched source files are in
`pingoasm/src/blender/`:

| File | Verified contents | Role |
| --- | --- | --- |
| `blenderaxes.png` | 34 × 34 RGBA; 10 colours; all 1,156 pixels opaque | Author's original artwork |
| `blenderaxes.rgba2` | 1,156 bytes; one RGBA2222 byte per pixel | Existing packed reference |
| `blenderaxes.rgba8` | 4,624 bytes; row-major R, G, B, A bytes | Existing RGBA8888 reference |

The existing `.rgba8` exactly matches the PNG's decoded RGBA bytes. After
approval, reproduce a project-owned RGBA8888 file from the PNG and compare it
with that reference. Preserve the PNG and existing RGBA2222 conversion; verify
the latter against the documented nearest-level quantization and
`AA BB GG RR` packing. The separate `blenderaxes1024.png` is a different source
and will not replace this matched 34 × 34 set.

Keep imported sources and a provenance/hash manifest under
`assets/bitmaps/source/`. Generate deployable raw files under
`tgt/assets/bitmaps/`; the app loads `assets/bitmaps/...` from `/extender`.
Record dimensions, pixel format, byte count, and derivation in the manifest.
The build should work from those project-owned inputs without requiring the
PingoASM checkout.

Derive the following clearly labelled controls alongside the unchanged art:

1. A geometric cutout version with transparent holes and a transparent border.
   Preserve meaningful black pixels in the axes artwork; do not use a blanket
   black colour key.
2. Alpha-value bands: RGBA8888 alpha 0, 1, 64, 128, and 255, and explicitly
   packed RGBA2222 alpha 0, 1, 2, and 3. The documented result is binary
   visibility: zero transparent, every nonzero value fully opaque. These
   formats do not promise alpha blending.
3. Distinct frame markers/tints, a few different frame sizes, and a common
   padded canvas for rotations. Preserve recognisable axes letters so flips,
   orientation, frame changes, and pivot errors remain visible.
4. Deterministic checker, stripe, and second-bitmap backgrounds with known
   physical RGB values; one monochrome mask and small packed-pixel examples.
   Use host-generated nearest-neighbour enlargements where a readable control
   must be independent of the VDP matrix implementation.

Both formats still display in the mode's 64 colours. RGBA8888 tests storage,
uploading, conversion, and rendering paths; it does not turn mode 20 into a
24-bit display mode.

## Authorized test pages

These stable BSP IDs describe reviewable tests, not a separate work checklist.
Each page includes both source formats where the command supports them and
where the comparison is meaningful.

1. **BSP-01 — Load and plot the original assets.** Load both raw formats
   through the buffered API, select with `VDU 23,27,&20`, and create with
   `&21,width;height;format` using formats 0 and 1. Compare one-block uploads
   with deliberately chunked uploads consolidated before bitmap creation.
   Show native 34 × 34 plots and independently enlarged controls, with source
   dimensions and byte counts. The two plots should show the same orientation
   and corresponding quantized colours. Validate file lengths before emitting
   a length-prefixed payload; missing/truncated files produce a recoverable
   application error, not a half-sent VDU command.

2. **BSP-02 — Legacy and 16-bit bitmap paths.** Compare legacy selection
   `23,27,0,n` with its alias buffer `64000+n`. Upload RGBA8888 using direct
   bitmap command 1 as well as buffered creation, then select/plot each through
   both addressing forms. Exercise command 2's solid-colour bitmap creation
   as a background/control. Use a separate buffer ID outside the legacy range
   to demonstrate genuine 16-bit addressing. Matching artwork should survive
   each selection change without one definition overwriting another.

3. **BSP-03 — Transparency and alpha values.** Plot the original, cutout,
   and alpha-band variants over stripes and a second bitmap. Zero-alpha holes
   reveal the exact background, including when their stored RGB is nonzero.
   Every nonzero alpha level remains equally visible. Compare both packed
   and unpacked formats and label this as an on/off mask test.

4. **BSP-04 — Bitmap PLOT variants and cursor movement.** Exercise PLOT
   `&E8–&EF`: absolute and signed relative positioning, foreground bitmap
   colours, background-colour silhouettes, and inverse drawing. Include
   negative and zero offsets, pure-move controls, and marked destination
   anchors. Foreground uses bitmap RGB and foreground GCOL; background uses
   the background colour/mode through the opacity mask. Inverse twice should
   restore the underlying pattern.

5. **BSP-05 — All eight bitmap paint modes.** Compare SET, OR, AND, XOR,
   invert, no-op, AND inverse, and OR inverse through bitmap PLOT and `VDU 18`.
   Use identical patterned panels for each format and small expected colour
   swatches calculated from physical RGB components. Include transparent
   regions, two successive XOR/invert draws, and a no-op control. Keep palette
   mappings fixed so logical colour numbers are not mistaken for pixel bits.

6. **BSP-06 — Bitmap-on-bitmap compositing.** Overlay the axes, a shifted
   or tinted axes variant, and a second pattern bitmap using OR, AND, and XOR.
   Reverse draw order on a paired panel and mark the intersection. Step
   through draw, redraw, and restoration; include XOR removal and a simple
   manually plotted moving-bitmap control with an explicitly restored
   background. Compare this manual process with the sprite pages later.

7. **BSP-07 — Direct drawing versus PLOT.** Compare `23,27,3,x;y;` with
   bitmap PLOT under a shifted graphics origin, logical coordinates, a small
   viewport, non-SET GCOL, and a selected matrix. Cross all four physical
   screen edges using opaque and cutout art. Direct drawing is documented
   to use pixel positions and bypass those graphics settings. Retain the
   known stock-reference clipping disagreement from SHP-23 as an explicitly
   labelled observation rather than adapting the expected contract to it.

8. **BSP-08 — Capture the screen into a bitmap.** Draw a known composite,
   establish the last two graphics positions, and capture using the 8-bit
   `23,27,1,n,0,0;` and 16-bit `23,27,&21,id;0;` forms. Replot the captured
   rectangle elsewhere and check inclusive bounds, including a one-pixel
   case. Modern VDP captures are RGBA2222. This page captures ordinary
   framebuffer graphics; hardware-sprite visibility is assessed separately.

9. **BSP-09 — Bitwise manipulation of bitmap bytes.** Copy the packed axes
   data into owned scratch buffers and use buffered command 5 adjustments
   for NOT, AND, OR, and XOR, including a second buffer as the operand source.
   Show one series that deliberately preserves the alpha bits and another
   that deliberately changes the opacity mask. Recreate/rebind the scratch
   bitmap as required before plotting. Compare byte-level results with host
   expectations; distinguish changing stored pixel bytes from painting pixels
   over the framebuffer with GCOL.

10. **BSP-10 — Monochrome masks and packed expansion.** Create format-2
    bitmaps from a 34-pixel-wide mask, using five bytes per row to expose
    padding/stride mistakes. Create the same mask under two foreground
    colours, then change GCOL and show that bitmap creation captured its
    colour. Exercise buffered expansion command 72 with 1-, 2-, and 4-bit
    inputs, inline and buffered colour mappings, and row alignment. Create
    RGBA2222 bitmaps from the expanded buffers explicitly. Off-mask pixels
    reveal the background; the expanded controls match their source patterns.

11. **BSP-11 — Matrix identity, selection, and clearing.** Enable affine
    transforms with `23,0,&F8,1;1;`, build identity using buffered command 32
    operation 0, and select it for bitmap plots with `23,0,&96,1,id;`.
    Compare with an untransformed plot. Change the selected matrix and plot
    again, then clear transform selection using ID 65535. Later plots should
    use the current matrix contents only while that transform is selected.

12. **BSP-12 — Scaling and reflections.** Exercise operation 5 with uniform
    2× and ½× scale, separate X/Y scales, and negative X/Y reflections.
    Compare scaling an identity matrix through operation 4 with operation 5;
    also include a translated matrix to expose operation 4 multiplying the
    first eight coefficients, including translation. Use corner markers and
    axes letters to distinguish a reflection from a misplaced bitmap.

13. **BSP-13 — Rotation in degrees and radians.** Exercise operations 2
    and 3 at 0°, 90°, 180°, 270°, and an oblique angle such as 30°. Pair
    equivalent degree/radian inputs. Show expected corner positions and
    rotation direction in the selected coordinate convention. Use exact
    orthogonal image references for strong comparisons and allow documented
    raster rounding at oblique edges rather than requiring identical pixels.

14. **BSP-14 — Translation and pivot placement.** Compare operation 6's
    pixel translation with operation 7's current-coordinate translation.
    Repeat under logical coordinates. Use operation 12's bitmap-relative
    translation to rotate/scale about the centre instead of the top-left,
    and compare with explicit pixel translations. Mark the bitmap transform
    origin separately from the PLOT anchor: transform coordinates start at
    the bitmap top-left even when the logical plotting convention differs.

15. **BSP-15 — Shear and skew.** Exercise X-only, Y-only, and combined
    shears with operation 8; compare skew angles in degrees/radians using
    operations 9 and 10. Draw reference parallelogram bounds and a modest
    grid behind the asymmetric artwork. Include opposite signs and reset
    identity between independent examples so matrices do not accumulate
    accidentally.

16. **BSP-16 — Composition order and inverse.** Compare translate-then-
    rotate with rotate-then-translate, and scale-then-rotate with the reverse
    order. Reproduce a composed result using operation 11's explicit six
    coefficients. Invert a known invertible matrix with operation 1 and
    compose the forward/inverse pair to recover identity. Mark pivots and
    expected bounds; omit undefined singular-matrix behavior.

17. **BSP-17 — Matrix argument formats.** Build equivalent transforms using
    float32, float16, fixed32, and fixed16 little-endian parameters. Include
    negative values, fixed-point fractions, and a fixed16 negative shift.
    Repeat with arguments fetched from a buffer and one operation whose
    arguments have individual format bytes. Use exactly representable values
    for equality checks and label any deliberately rounded examples.

18. **BSP-18 — Bake transformed bitmaps.** Use buffered command 40 on both
    source formats. Compare unchanged canvas size, automatic bounds, explicit
    dimensions, and automatic translation of the minimum transformed corner
    to the new top-left. Show fixed-canvas clipping versus a fitted result,
    with rotation, scaling, and reflection. Every output is RGBA2222,
    including results baked from an RGBA8888 source. Compare ordinary plots
    of the baked result with the corresponding live PLOT transform.

19. **BSP-19 — Reuse and restore bitmap drawing state.** Draw the same
    transformed motif directly and through a reusable command buffer. Save
    and restore context around changes to selected bitmap, matrix selection,
    paint mode, origin, and viewport, then repeat the reference plot. Confirm
    that bitmap/buffer definitions are global resources, so restoring a
    context does not roll back modifications to matrix or image bytes. Clear
    transform selection explicitly before proceeding to sprite comparisons.

20. **BSP-20 — Software sprite lifecycle.** Use selection, frame clearing,
    8-/16-bit frame addition, activation, show/hide, and explicit software
    selection: `23,27` commands 4–7, 11, 12, 20, and `&26`.
    Present both original formats plus a cutout control. Activate contiguous
    sprite IDs and show that hiding preserves the definition, while clearing
    its frames leaves that sprite with nothing to draw. Add a mono/mask
    software frame to demonstrate its supported format boundary.

21. **BSP-21 — Absolute and relative sprite movement.** Compare commands
    13 and 14 with matching paths, including negative and zero deltas and
    partially off-screen positions. Move multiple sprites before one update.
    Check that sprite positions remain pixel-based when graphics origin and
    logical scaling change. Exercise the library's fixed-point convenience
    position helpers against integer-pixel controls, with documented rounding
    and caller origin inputs; these helpers do not add fractional VDU fields.

22. **BSP-22 — Deferred update and background restoration.** On successive
    keypresses, stage a software move without command 15, then issue the
    explicit update. Repeat with an ordinary drawing operation as the update
    trigger. Preprint stage instructions and hide the text cursor so label
    output/cursor flashing cannot accidentally trigger the first update.
    Move and hide the sprite over a detailed background; the vacated region
    should recover correctly. Observe the deferred stage through actual
    display captures without injecting intervening drawing commands.

23. **BSP-23 — Animation and frame replacement.** Step next, previous,
    wraparound, and explicit frame selection using commands 8–10. Replace
    the selected frame using 8-bit command 21 and 16-bit `&35`.
    Use recognisably different axes frames, both RGBA formats, and different
    dimensions. Exercise documented ignored cases such as an out-of-range
    frame selection or adding an undefined bitmap, followed by a valid
    operation that demonstrates the sprite remains usable.

24. **BSP-24 — Software sprite paint modes.** Use command 18 for all eight
    GCOL modes over checkerboards and other bitmaps, with both formats and
    transparent holes. Compare corresponding BSP-05 bitmap plots. Step
    repeated updates, frame changes, movement, and hiding; repainting a
    stationary XOR sprite should remain stable, and removal should restore
    its background rather than leave an XOR trail.

25. **BSP-25 — Software overlap and activation.** Overlap several software
    sprites with identifiable borders and holes to show drawing priority.
    Vary the active contiguous prefix, hide an interior ID, move front and
    rear sprites, change a frame, and redraw background graphics under them.
    Check layering and restoration where several saved backgrounds overlap;
    changing one sprite should not erase another.

26. **BSP-26 — Hardware sprite basics.** Enable hardware sprites with
    `23,0,&F8,2;1;` and command 19. Compare RGBA2222 and RGBA8888 opaque and
    cutout frames, show/hide, and absolute/relative movement. Hardware changes
    should appear without command 15. Convert a sprite back with command 20
    and repeat the software update control. Keep hardware and software results
    separately labelled if the reference emulator lacks an expected feature.

27. **BSP-27 — Mixed sprite layering.** Overlap hardware sprites, software
    sprites, and subsequently drawn bitmap/vector graphics. Hardware sprites
    should remain above framebuffer graphics and software sprites; higher
    hardware IDs should appear above lower ones. Step hide/show and backend
    conversion to make priority changes visible. Include transparent holes
    that reveal the next layer.

28. **BSP-28 — Hardware paint-mode exceptions.** Demonstrate that command
    18 changes a hardware sprite back to software. Then apply XOR with command
    18 followed by hardware selection 19: VDP 2.15 documents XOR for RGBA2222
    hardware frames, while RGBA8888 hardware frames use SET. Compare other
    requested paint modes, which also use SET in hardware. Label the expected
    fallback and the command order; do not silently replace hardware tests
    with software results.

29. **BSP-29 — Transformed sprite frames.** Feed BSP-18's baked rotations,
    reflections, and scales into software and hardware sprite frame lists.
    Compare a fixed padded canvas, which preserves the intended pivot, with
    tightly fitted frames whose offsets/sizes vary. A currently selected
    bitmap PLOT matrix should not transform ordinary sprite frames. Include
    independent RGBA8888 orthogonal frame controls; label VDP-baked frames
    as RGBA2222 rather than suggesting command 40 preserves the source format.

30. **BSP-30 — Bounded sprite population.** Step through 1, 2, 4, 8, and
    16 sprites, comparing shared versus distinct frames, both RGBA formats,
    and software versus hardware. Compare staggered positions with sprites
    sharing scanlines, and include a modest larger-frame example. Move the
    group in one step and record missing sprites, flicker, or corruption.
    This is a bounded visual workload, not an emulator-derived claim about
    Extender's maximum sprite count or hardware throughput.

31. **BSP-31 — Shared frame and buffer lifecycle.** Share one bitmap between
    multiple sprites, replace one sprite's selected frame, and demonstrate
    that the other frame binding stays intact. Hide/detach affected sprites
    before altering or recreating a shared bitmap, then rebind and show them.
    Reload original asset bytes and compare with a fresh control. Exercise
    loader error recovery without sending truncated packets or deliberately
    leaving a live sprite referring to freed storage.

32. **BSP-32 — Reset, cleanup, and rerun.** Compare sprite-only reset 17
    with bitmap-and-sprite reset 16. The former retains bitmap definitions;
    the latter clears the screen and definitions but retains their buffer
    bytes. Recreate the bitmaps from those retained bytes, rebuild a small
    scene, then perform explicit app-owned cleanup. Redraw the heading after
    the reset that clears it. Verify normal completion, Escape from staged
    pages, and a second launch without stale sprites, matrix state, or assets.

## Implementation boundaries

1. Build to `tgt/bitmaps.bin`, keeping the existing applications available.
   Deployment follows the accepted layout: app binaries in `/extender`,
   supporting files in `/extender/assets/bitmaps`. When implementation is
   approved and ready, select the new app explicitly in mode-20 startup and
   launch the canonical `.emulator` profile for Author review.
2. Audit each exercised Nurples entry point and its actual transmitted bytes.
   Pair representative wrapper calls with literal-packet controls so a library
   defect can be distinguished from a VDP discrepancy. Fill missing wrappers
   through application-neutral adapters or documented fixes that preserve
   vendor provenance. The current snapshot lacks several newer sprite
   commands and contains buffered-API placeholders.
3. Use exact 16-bit protocol fields in ADL mode. Keep asset validation and
   application presentation outside generic APIs. The inherited file loader's
   unchecked handle and fixed scratch address need an audited replacement or
   repair before use; use bounded reads and application-owned staging memory.
   Keep each raw payload uninterrupted once its length has been emitted.
4. Allocate a documented namespace for buffers, matrices, frames, and the
   required legacy bitmap aliases. Use sprite IDs 0–15 for the population
   test. Reset is intentionally tested in a dedicated application session;
   normal cleanup clears only resources owned by this app. Hide/deactivate
   and detach sprites before freeing their frame storage.
5. Use MOS/EMOS output and keyboard services, with bounded response waits.
   Keep the imported direct timer/interrupt helpers dormant. Flush drawing
   before observation where appropriate, but do not accidentally trigger a
   refresh in the deferred-update test. Restore owned contexts, transform
   selection, test flags changed by the app to the documented demo baseline,
   text cursor, colours, origin, and viewports on exit, without changing mode.
6. The coverage is 2D bitmap/sprite behavior. General matrix algebra, 3D
   transforms/meshes, mouse cursors, audio, and a complete buffered-command
   interpreter suite are outside this app. Reserved native bitmap format 3
   and undefined or deliberately dangerous resource-lifetime behavior are
   excluded. Experimental affine/hardware features remain visibly labelled.

## Validation and review evidence

1. Validate imported hashes, generated dimensions/lengths, channel order,
   RGBA2222 packing, alpha masks, frame metadata, and build reproducibility.
   Assemble with symbols/listing and independently audit new packet layouts,
   buffer bounds, and exercised library entry points. These checks should
   catch transport/asset errors before interpreting an image discrepancy.
2. Use a small independent set of expected pixels and image bounds for exact
   cases: basic plots, alpha masks, GCOL arithmetic, identity and orthogonal
   transforms, clipping, capture, and software background restoration. Use
   labelled visual comparisons for oblique rasterization and workload effects.
   Avoid having the packet generator supply its own unquestioned oracle.
3. Exercise the complete tour and every page independently in the stock
   reference emulator, including staged keys, Escape, load failures, cleanup,
   and rerun. Save actual presentation frames and per-stage results. Record
   packet validity, observed rendering, timeouts, and missing support as
   distinct outcomes; tour completion alone is not a rendering PASS.
4. Hardware sprites are composited during display scanout and need not appear
   in framebuffer pixel queries or captured-screen bitmaps. Validate them from
   the actual emulator presentation where supported, followed by the physical
   Extender display. Treat missing emulator scanout support separately from
   a failed hardware-sprite command; retain compiled tests for Extender review.
5. Keep documented expectations and reference discrepancies side by side,
   following Shapes. Physical Extender qualification and Author visual
   acceptance are separate records. Emulator-related changes remain
   uncommitted until the Author has tested them and explicitly approved a
   commit. The Author subsequently authorized the complete implementation.

   BSP-28 exercises that specific versioned contract explicitly.
