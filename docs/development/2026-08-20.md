# Development Log — 2026-08-20

## Initial repository and VDP setup planning

The new Agon Extender repository was established as a clean lineage separate
from the private legacy repository. Initial product intent, hardware, firmware,
core transport, networking, display expansion, and licensing information was
published in the root README.

Local, ignored agent guidance now points to the canonical Agon development
environment and maintains task details, official-repository links, and reusable
technical précis documents. `TODO.md` is the single authoritative tracked list
of unfinished work.

`SETUP-001` began the initial PlatformIO and VDP-port setup. A read-only audit
compared official `agon-vdp` at commit `c7ac293d2aa81ddfa693390549bcd909069c8fc3`
with the legacy Extender at commit
`df54cf6a7a23cd40e98076856f68cff0559d1c77`.

## SETUP-D001 — Extender source location

Accepted `vdp/video/extender/` as the ownership boundary for new Extender
capabilities. Keeping it beneath the official PlatformIO source directory
simplifies source discovery and includes while preserving every existing
upstream file at its official relative path. The sibling alternative
`vdp/extender/` offered a visually purer upstream tree but required additional
build-system machinery.

The normative architecture was added to `docs/architecture.md`; full rationale
and consequences are retained in
`docs/decisions/ADR-0001-vdp-source-layout.md`.

## SETUP-D002 — Firmware framework

Accepted a hybrid Arduino and ESP-IDF environment under PlatformIO. PlatformIO
preserves the official VDP project's familiar project and command workflow;
Arduino preserves its sketch lifecycle and source APIs; ESP-IDF supplies the
P4-specific configuration and native facilities required by Extender.

The decision remains subject to a minimal hybrid build and physical-board
canary before official VDP source is imported. The normative design is in
`docs/architecture.md`, with rationale and consequences in
`docs/decisions/ADR-0002-hybrid-firmware-framework.md`.

## SETUP-D003 — Platform package baseline

Accepted pioarduino release `55.03.311` as the pinned PlatformIO platform
baseline. It supplies Arduino-ESP32 3.3.11 and ESP-IDF 5.5.5, retains the IDF
version already exercised by the legacy P4 project, and includes an ESP32-P4
revision fix.

The numbered release replaces both a moving `stable` alias and the legacy
development commit as the production candidate. The legacy setup remains a
hardware-configuration reference and fallback. The selected release remains
subject to the same minimal hybrid build and physical-board qualification gate
as SETUP-D002. See
`docs/decisions/ADR-0003-pioarduino-platform-baseline.md`.

## SETUP-D004 — P4 silicon identity

Accepted `esp32p4_es` as the PlatformIO chip variant for the Rev-D1 board's
v1.3 ESP32-P4. The SDK configuration will explicitly retain the legacy-proven
pre-v3 full revision range 100 through 199 instead of relying solely on
platform-generated defaults.

The bring-up canary must report the runtime chip revision, verify that the
generated SDK configuration retained the intended bounds, and treat a mismatch
as a failed qualification. See
`docs/decisions/ADR-0004-p4-silicon-identity.md`.

## SETUP-D005 — Flash bus mode

Accepted QIO at 80 MHz as the qualification candidate for the board's 16 MB
SPI flash. DIO at 80 MHz remains the explicit fallback. This does not yet claim
that QIO is physically qualified: the canary must confirm the boot-reported
mode, frequency, and capacity and pass repeated cold-boot, reset, reflash, and
flash-integrity testing.

The decision reconciles the legacy board definition's deliberate QIO setting
with the legacy generated SDK configuration's DIO default by testing the
higher-performance supported candidate rather than treating either file as
conclusive hardware proof. See
`docs/decisions/ADR-0005-flash-bus-mode.md`.

## SETUP-D006 — Board memory model

Accepted a 512,000-byte PlatformIO internal-RAM link budget, matching the
pioarduino pre-v3 P4 evaluation-board baseline, while declaring the board's
32 MB PSRAM separately in hexadecimal mode at 200 MHz.

This replaces the legacy board definition's misleading use of 32 MB as
`maximum_ram_size`. Bring-up must detect the full PSRAM capacity and pass its
memory test. Bulk buffers will use PSRAM deliberately, while stacks,
latency-sensitive state, interrupt data, and peripheral-constrained buffers
remain in internal RAM unless proven safe elsewhere. See
`docs/decisions/ADR-0006-board-memory-model.md`.

## SETUP-D007 — Flash partition strategy

Accepted two equal 7 MiB OTA application slots within the board's 16 MB flash,
with automatic rollback and explicit post-boot validation. No permanent factory
application will be maintained; the previous OTA image is the normal recovery
target, while the P4 ROM download mode over USB remains the ultimate recovery
path if neither application boots.

NVS, OTA selection metadata, and crash diagnostics receive the required leading
data space. Approximately 1.9 MiB remains reserved without committing it to a
filesystem. Exact offsets will be frozen only after the pinned hybrid toolchain
generates a valid baseline partition table. See
`docs/decisions/ADR-0007-flash-partition-strategy.md`.

## SETUP-D008 — Hybrid CMake boundary

Accepted a no-project-CMake starting point. PlatformIO will generate and manage
the initial Arduino/ESP-IDF hybrid build structure. A tracked CMake file will be
introduced only if the minimal canary demonstrates a concrete component,
dependency, source-discovery, or SDK integration requirement that PlatformIO
cannot express directly.

Any required CMake must remain minimal and must not reorganize the
upstream-compatible `vdp/video/` source tree. See
`docs/decisions/ADR-0008-minimal-cmake-boundary.md`.

## SETUP-D009 — PlatformIO command wrapper

Accepted `scripts/vdp-pio.sh` as a transparent pass-through to the repository's
`.venv/bin/pio`, with `vdp/` selected as the project directory. The wrapper may
locate paths and validate prerequisites but will not rename PlatformIO commands
or perform implicit builds, uploads, installs, device selection, or environment
activation.

Direct `.venv/bin/pio` use remains supported. See
`docs/decisions/ADR-0009-platformio-wrapper.md`.

## SETUP-D010 — CPU frequency

Accepted the Olimex vendor-rated 400 MHz CPU frequency as the primary
qualification target. The same setting was exercised by the legacy project,
while pioarduino's generic pre-v3 board uses a more conservative 360 MHz.

The canary must verify the runtime frequency and pass sustained CPU, flash,
PSRAM, and mixed-load tests. If instability appears at 400 MHz, the same tests
must be repeated at 360 MHz before assigning the fault to another subsystem.
See `docs/decisions/ADR-0010-cpu-frequency.md`.
