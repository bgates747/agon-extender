## SETUP-006.4 beta GPIO boundary

The Author accepted circuit simplicity over transparent reuse of the eleven
eZ80 GPIOs consumed by the Exclusive Extended transport for the first beta
carrier. Beta will not add passthrough multiplexing, event capture, signal
replay, output holding, or GPIO virtualization. Direct use of transport-owned
GPIOs while the enhanced transport is active is therefore an explicit beta
compatibility carve-out; saved and restored eZ80 register state is not an
electrical-transparency guarantee.

Possible v1 multiplexing remains an active design consideration intended to
narrow that carve-out and strengthen the backward-compatibility claim. The
beta layout review should avoid needlessly foreclosing that path without
adding speculative circuitry before its signal-retention contract and
implementation are selected.

The Author then accepted the bounded beta GPIO allocation and transport
decisions. Beta provisionally preserves GPIO6, GPIO18, GPIO19, and
GPIO46--GPIO48 as six uncommitted exposed user candidates subject to capability
verification, reserves GPIO37/GPIO38 for optional MOD-WIFI-ESP8266 UART use,
and reserves no pins for the post-v1 VDP/EDP link. The eleven transport-owned
eZ80 contacts receive labeled test points only. P4 GPIO16 becomes dedicated
return-UART TX while GPIO12 remains PARLIO D1 input. The first General Poll
beta omits `UART_ALLOW_N`; PD6/GPIO17 and practical routing space remain
unassigned pending PORT-008 evidence.

Permanent v1 user-GPIO guarantees, replicated eZ80 headers, passthrough
switching, lease semantics, output holding, event capture and delivery,
transparent support for timing-sensitive direct-GPIO applications, public-GPIO
qualification fixtures, and direct VDP/EDP link pin reservations were
explicitly deferred. SETUP-006.4 Q003--Q006 remain open.

The Author subsequently deferred Q003 rather than selecting the split-power
production buffer architecture before firmware evidence exists. PORT-008 now
begins its bounded prototype with a forward-only stage using the existing
controlled-power predecessor circuit under strict power discipline. New EMOS
and EDP firmware must transfer real official command bytes over the parallel
bus and visibly execute representative simple display commands while the UART-
return driver remains disabled. This can prove forward transport, parser
integration, pin use, and visible execution; it cannot qualify reverse UART,
either-order power, partial-power-down behavior, or the eventual beta circuit.
Q003 returns for disposition after that evidence is reviewed; Q004--Q006 remain
open now.

The Author likewise deferred Q004. The forward-only tranche may exercise
READY_N admission and backpressure through the predecessor's direct
GPIO20/open-drain connection only under controlled power. That result cannot
approve the direct path for beta or establish reset, powered-off, back-power,
or hardware-safe-release behavior. Selection of the proposed isolated
NPN/NMOS READY_N stage follows the forward evidence; Q005--Q006 remain open.

The Author accepted and physically resolved Q005. Olimex marks optional R31,
which could link GPIO23 to the Ethernet RMII clock, DNP. Direct inspection of
the underside of the current Rev D1 bench board found solder on the two R31
pads but no resistor or other bridging component. GPIO23/EXT2-10 is therefore
retained as forward data bit D2; Q006 was the remaining open question at that
review point.

The Author deferred Q006 and stopped production-tuning discussion. Series
resistance remains an experimental property of the predecessor wiring until a
concrete beta circuit is proposed and measured. The critical path is the actual
retained VDP port: complete the minimum ported display/parser path needed for
visible behavior, then use PORT-008 to send official command bytes over the
current controlled-power forward wiring. No throwaway protocol or standalone
test firmware substitutes for that port. SETUP-006 is paused behind this
evidence, and no coding was authorized by this bookkeeping change.
