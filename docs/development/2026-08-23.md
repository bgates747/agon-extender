# Development log — 2026-08-23

## Operating-mode audit and vocabulary

QUAL-001 Review Gate 2 exposed that the candidate three-mode matrix conflated
two distinct P4-exclusive profiles. The Author clarified and accepted four
formal operating modes:

- **Legacy mode** (`mode:extender:legacy`): Extender is inactive and behaves as
  if absent;
- **Exclusive Compatible mode**
  (`mode:extender:exclusive-compatible`): the EDP is exclusive and uses the
  stock VDP UART transport contract;
- **Exclusive Extended mode** (`mode:extender:exclusive-extended`): the EDP has
  the same exclusive compatibility authority and uses the enhanced
  parallel-forward/UART-return transport; and
- **Dual mode** (`mode:extender:dual`): the onboard VDP owns ordinary VDU and
  canonical stock state while EDU addresses the active EDP separately.

“Compatible” and “Extended” are accepted short forms in unambiguous mode
context. “Exclusive” remains mandatory in both official exclusive-mode names.
Dual means two active, separately addressed processors; it does not authorize
mirrored VDU traffic, competing response streams, or shared canonical sysvar
ownership.

The audit also corrected the stock-UART hardware assumption.
`light2-harness-r01` belongs to the predecessor's enhanced split-link design and
is not a candidate stock-UART implementation. Exclusive Compatible firmware
requirements will be developed and tested without waiting for hardware. Once
those requirements are mature enough to drive circuitry, the project will
create a separate hardware design-review task, produce a new versioned design,
and qualify it from first principles.

QUAL-001 Review Gate 2 remains paused until the four-mode model and remaining
SETUP-005 boundaries are reflected in reviewed qualification data.

## Mode-lifecycle foundation

The Author accepted REMED-001 `W2D-Q01`. Formal operating mode is derived from
two separately owned state planes: the MOS-owned ordinary-VDU route and the
EDP-service activation state. Their four supported combinations map exactly to
Legacy, Dual, Exclusive Compatible, and Exclusive Extended. An exclusive route
with inactive EDP is invalid. Introducing another independent state dimension
requires explicit architectural review because it would multiply lifecycle,
transition, failure, and qualification combinations.

The Author then accepted REMED-001 `W2D-Q02` with staged scope. Legacy and Dual
may transition live because their ordinary VDU route remains onboard. The
proof-of-concept/beta baseline uses a disruptive controlled restart for any
ordinary-VDU route change and may remain the v1 fallback. Preserving loaded
eZ80 program/data and resident processor state is an aspirational v1 target and
a firm v2 requirement under MODE-001. That requirement preserves state in
place where specified; it does not imply automatic migration of display assets
between onboard VDP and EDP.

The Author accepted REMED-001 `W2D-Q03`. Mode activation follows a common
prepare/readiness/commit/recover transaction: it validates and initializes all
prerequisites before publishing new routing, commits only a complete supported
two-plane state, and restores a stable mode after bounded pre-commit failure.
One-shot pending attempts prevent an invalid target from causing an
infinite restart loop. This coherence contract does not itself promise eZ80 or
display-state preservation.

The Author amended REMED-001 `W2D-Q02` and accepted `W2D-Q04`. Legacy is the
mandatory transition hub, so a request between two non-Legacy modes must
complete a safe return to Legacy before attempting its destination. Every cold
boot reaches fully operational Legacy and makes no Extender contact unless an
explicit late `autoexec.txt` or manual invocation occurs. A successful explicit
presence/version probe activates EDP and commits Dual; failure leaves Legacy.
Exclusive entry begins only after Legacy and is never a direct cold-boot mode.
Persisted preferred-mode selection remains an exploratory possible v1 feature,
not a v1 contract. One-shot pending transaction state remains a separate
safety mechanism.

The Author accepted REMED-001 `W2D-Q05` with structured failure reporting.
Detected EDP failure in Dual invalidates EDU work and commits Legacy while the
onboard VDU continues. Exclusive EDP/transport failure blocks new VDU, permits
only bounded reinitialization, and otherwise recovers disruptively to Legacy
without claiming that application or display state survived. Structured crash
reporting is advisable during beta and a hard v1 requirement, not a beta gate.
To the extent possible, failures must explain the failed component, mode,
recovery, and practical consequences onscreen and in a durable
machine-readable log. Truthful bounded eZ80 PC/register/stack and P4 exception
context should be included where safely obtainable. DIAG-001 owns
implementation and qualification of this reporting path.

The Author accepted REMED-001 `W2D-Q06`. Reset invalidates the affected
component's sessions, parsers, pending work, readiness claims, and authority
even if its RAM bytes or another processor survive. Invalidation does not
itself erase retained state. eZ80/MOS and whole-system resets return through
Legacy; P4 reset in Dual commits Legacy; exclusive P4 reset follows bounded
reinitialization and Legacy fallback; and onboard-VDP reset in an exclusive
mode leaves input unavailable until private reinitialization succeeds.

The Author initially accepted REMED-001 `W2D-Q07`. Extender-enabled MOS is one complete
backward-compatible replacement for stock MOS, not a side-by-side companion,
and its dispatcher alone owns ordinary VDU routing. EDU integration owns EDP
activation in Legacy/Dual. Formal mode is derived from the committed routing
and EDP-service planes rather than a competing mode variable. Runtime records
cover requested, one-shot pending, committed, failure, and fallback state;
persisted user preference is not a v1 contract. Exact commands, APIs, storage,
formats, and data structures remain deferred. Fixed-backend development builds
still boot Legacy and require explicit activation. The later EMOS-only decision
recorded below supersedes the separate EDU-integration owner.

The Author accepted REMED-001 `W2D-Q08`. Successful explicit probe/activation
latches Dual as system state; it does not end when the initiating utility exits
or no foreground callers remain. Normal shutdown is explicit, coordinates with
registered work, and may refuse or time out safely when owners cannot quiesce.
A separately explicit forced shutdown may invalidate outstanding work after
warning. Completion deactivates EDP and commits Legacy. P4 reset/failure follows
the accepted Q05/Q06 recovery path; exact session and shutdown APIs remain
deferred.

## Actor-explicit proposal rule

The Author required all subsequent proposals to name the processor, firmware,
software, hardware circuit or wiring, host, or operator performing each
material action. Traffic descriptions must identify sender, receiver,
transport owner, and physical wiring where known; request, authorization,
execution, storage, observation, reporting, and recovery must not be collapsed
into an ambiguous “system” actor. Unknown ownership must be identified
explicitly and assigned to a tracked task.

During REMED-001 `W2D-Q09` review, prohibited item 6 was refined accordingly:
the Extender-enabled MOS mode-transition coordinator owns bounded attempts,
one-shot pending state, Legacy fallback, and protection against automatic
`autoexec.txt` or future persisted-preference retry loops. Retry after failure
requires a new authorized attempt. Q09 remains open pending the other items.

That item was subsequently narrowed after the Author identified that preventing
an unchanged `autoexec.txt` command from reissuing a request across full resets
requires a retained flag or equivalent command cooperation. The Author coined
**Extender MOS (EMOS)** for the single complete backward-compatible MOS
replacement. EMOS makes one attempt per explicit request and does not
autonomously re-arm it. Cross-boot circuit breaking is not a beta requirement;
MODE-002 will use regression evidence to determine whether it should become a
v1 target and what retained state or API contract would enforce it. Q09 item 6
is accepted only at this narrowed boundary.

The Author accepted REMED-001 `W2D-Q09.3` as a hard-v1 pull-discovery policy.
EDP/P4 firmware and carrier wiring must remain quiescent while Legacy is
committed or a mode transaction is uncommitted. EMOS prepares the eZ80-side
receiver, initiates discovery, validates the EDP response, and alone commits a
mode. Negotiated asynchronous EDP traffic is permitted only after activation;
P4 reset revokes that permission and EMOS quarantines stale traffic. Rev 1
defines no proactive presence signal. QUAL-002 now owns late P4 power-on,
either-order power/reset, electrical isolation, boot chatter, stale traffic,
bounded readiness, and no-mainboard-reset Legacy-to-Dual qualification.

The Author accepted REMED-001 `W2D-Q09.1`. A reviewed transport/wiring profile
must be selected before exclusive entry. EMOS arms the eZ80 receiver and sends
the readiness request; EDP/P4 firmware returns compatible identity, protocol,
and capability data; and EMOS alone commits the exclusive route. A successful
handshake proves protocol readiness but does not electrically qualify carrier
wiring; QUAL-002 remains the physical authority.

The Author accepted REMED-001 `W2D-Q09.2`. EMOS contains one fixed set of
modified `RST.LIL 10h`, `RST.LIL 18h`, and C-runtime output handlers feeding a
single VDU dispatcher; mode changes do not swap reset-vector tables. Each
dispatcher invocation snapshots one backend. The EMOS coordinator blocks new
calls, waits for active calls and owned response work to finish or be
abandoned, reinitializes affected parser state, and commits the backend
atomically. Beta adds no second semantic VDU parser and does not promise that a
running application can carry a multi-call partial command through the
disruptive transition.

The Author accepted REMED-001 `W2D-Q09.4`. The EMOS dispatcher, EDP/P4
firmware, and carrier wiring never mirror ordinary application VDU to both
processors. Legacy/Dual deliver it only to onboard VDP; exclusive modes deliver
it only to EDP. Private input/bootstrap control, recovery diagnostics, and
separately identified qualification traffic remain targeted exceptions rather
than duplicated application output.

The Author accepted the VDU/EDU call and destination boundary during the Q09
review. `RST.LIL 10h`, `RST.LIL 18h`, and C-runtime output remain conventional
VDU calls while EMOS selects their destination: onboard VDP in Legacy/Dual,
EDP compatible backend in Exclusive Compatible, and EDP enhanced backend in
Exclusive Extended. Explicit EDU calls retain a separate versioned interface
and result domain. Applications may deliberately combine both call classes;
this is a mixed-API program, not another operating mode. A program may also
require Exclusive Extended and use conventional VDU restarts for efficient
compatible output, provided it verifies or requests the required mode before
issuing mode-sensitive traffic.

The Author superseded the stock-MOS Dual assumption. Every active Extender mode
now requires EMOS; stock MOS supports only Legacy, where Extender remains
inactive. Linked EDU code is permitted only as an EMOS API binding, not as an
independent UART/GPIO/vector or lifecycle owner. Deliberate direct-hardware
experimentation remains physically possible but is unsupported and caveat
emptor.

The Author also accepted a hard pre-activation non-destruction requirement.
Carrier hardware must default P4-to-Agon drivers disabled independently of P4
firmware and tolerate arbitrary legal eZ80 logic/direction activity within the
documented electrical envelope without contention damage, back-powering, or
persistent corruption. Before activation, EDP firmware exposes only a bounded,
staged EMOS transaction recognizer; ordinary VDU, EDU, update, and persistent
write operations remain unreachable. Any unmanaged-traffic warning is
best-effort, out-of-band on an Extender-owned sink, and must never weaken
electrical isolation or transmit over unactivated Agon-facing wiring.

The Author accepted REMED-001 `W2D-Q09.5`. EMOS may use the onboard VDP for
recovery diagnostics or restored Legacy output after exclusive EDP failure only
after explicitly disclaiming application/display continuity. It must not claim
that lost or unknown EDP display, audio, buffer, or application-visible state
survived.
